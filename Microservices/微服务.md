# 微服务

以电商项目为例，看架构是怎么一路演进的。

## 架构演进

### 单体架构（Monolith）

项目初期，所有功能塞在一个应用里，CRUD 一把梭，先 run 起来再说，然后不断堆功能。

优点：开发快、部署简单、测试方便。缺点：功能一多，代码耦合严重，编译部署越来越慢，一个小改动可能拖垮整个系统。

### SOA（面向服务架构）

业务变大后开始拆分、重构，把公共能力抽成服务，通过 ESB（企业服务总线）统一调度。强调组件化、服务复用。

### 微服务

后期进一步细化，按业务边界把系统拆成一个个独立的小服务，各自部署、各自扩展，用轻量协议（HTTP/RPC）通信。

> SOA 偏组件化，微服务偏服务化。本质都是拆分，但微服务粒度更小、更强调去中心化和独立部署。

## 优势和挑战

### 优势

- **快**：敏捷开发，快速交付
- **准**：服务粒度小，质量精准可控
- **狠**：迭代周期更短，试错成本低

### 挑战

分布式系统很复杂：

- 服务依赖不好管理
- 数据一致性难保障
- 测试困难（要模拟一堆下游）
- 对 DevOps 基础设施要求高（监控、日志、链路追踪、CI/CD 一个都不能少）

## RPC

### 什么是 RPC

RPC（Remote Procedure Call，远程过程调用）：客户端通过网络向服务端发请求，服务端执行完把结果返回，看起来就像调本地函数一样。相对的概念是本地调用（同一进程内）。

本地调用的大致过程：

1. 把实参压入栈
2. 函数从栈里取值，赋给形参
3. 执行函数，返回值入栈
4. 退出函数，拿到返回值

本地调用之所以简单，是因为发生在同一进程、共享同一块内存。

### RPC 要解决的三个问题

app1 想调 app2 的函数，但两个进程内存相互隔离，所以：

1. **怎么定位函数**：本地调用靠内存地址和指针；远程得维护一张「函数名 → 实现」的映射表（服务注册）。
2. **怎么传参数**：内存地址传不过去，要序列化成字节流（编码 / 解码）。
3. **怎么传输**：走 TCP 或 HTTP 把字节流发过去。

### RPC vs RESTful

HTTP + RESTful API 也能实现远程调用（写个 HTTP server，JSON 塞请求体里），但每次要手动处理编码，比较麻烦。

- RPC 让跨服务调用像本地调用一样简单
- RESTful 基于 HTTP，RPC 多用 TCP，传输效率更高
- RESTful 多用于前后端数据传输，RPC 多用于微服务之间的内部调用

### 一个基础的 RPC 例子（Go）

Go 标准库自带 `net/rpc`，可以把对象的方法暴露成远程服务：定义一个结构体，给它加方法，这个结构体就能当服务用。不过它用的是 gob 编码，且不能注册同一类型的多个对象。

RPC 还支持跨语言调用，只要协议和编码约定一致就行。

RPC 原理总结：

1. 客户端调 stub，传入方法名和参数
2. client stub 把参数打包（序列化），通过网络发出去
3. 服务端收到后按协议解析出参数
4. 服务端执行本地函数，得到结果
5. 结果原路返回给客户端

打包、解包都由框架提供，业务代码只关心调用本身。

## gRPC

### 是什么

Google 开源的 RPC 框架，用 HTTP/2 作为传输协议（比 HTTP/1.1 改进很多：多路复用、头部压缩、双向流）。

gRPC 的做法：先在 `.proto` 文件里定义服务（方法名、参数、返回类型），然后自动生成客户端和服务端代码。客户端拿到一个 stub，实现了和服务端相同的方法。

社区里还有其他 RPC 框架，但 gRPC 是最通用的一个。

### 为什么用 gRPC

- 一份 `.proto` 文件定义服务，支持任意语言生成客户端和服务端（跨语言）
- 借助 Protocol Buffers 高效序列化，体积小、速度快
- 接口更新容易（加字段不影响旧客户端）
- IDL（接口描述语言）让不同语言、不同平台的对象能互相通信

### 四种调用模式

1. **Unary（一元）**：一发一收，最常见的普通调用
2. **Server Streaming（服务端流式）**：客户端发一次请求，服务端返回一串消息
3. **Client Streaming（客户端流式）**：客户端发一串消息，服务端返回一次响应
4. **Bidirectional Streaming（双向流式）**：双方各发一串消息，顺序随意

## Protocol Buffers 语法

### 消息类型

```proto
syntax = "proto3";   // 第一行必须声明版本

message Person {
  string name = 1;   // 字段编号，在二进制中标识字段
  int32  age  = 2;
}
```

- `syntax` 必须是第一行（注释除外）
- `message` 类似 Go 的结构体
- 字段编号唯一，一旦使用就不能改；1~15 编号占 1 字节，16~2047 占 2 字节，常用字段放前面更省

### 字段规则

- 普通字段（singular）：可以传 0 个或 1 个
- `repeated`：可以传多个，最终变成类似数组

### 字段类型

| proto 类型 | Go 类型 | 说明 |
| --- | --- | --- |
| double | float64 | |
| float | float32 | |
| int32 / int64 | int32 / int64 | 变长编码，负数效率低 |
| uint32 / uint64 | uint32 / uint64 | 变长 |
| sint32 / sint64 | int32 / int64 | 变长，负数友好 |
| fixed32 / fixed64 | uint32 / uint64 | 固定 4 / 8 字节 |
| sfixed32 / sfixed64 | int32 / int64 | 固定 4 / 8 字节 |
| bool | bool | |
| string | string | UTF-8 |
| bytes | []byte | |

其他都差不多，不一一列了。

### 默认值

解析消息时，如果某个 singular 字段没传值，就用默认值：数字 0、字符串空串、bool false、枚举第一个值（编号必须为 0）、message 为未设置。

### 枚举

```proto
enum Status {
  UNKNOWN = 0;   // 编号从 0 开始
  RUNNING = 1;
  STOPPED = 2;
}
```

- 前面加 `enum`，编号从 0 开始
- 可以在消息内定义，也可以在外面定义，成为独立类型
- 枚举值命名推荐全大写 + 下划线
- 多个枚举值指向同一个编号（别名）需加 `option allow_alias = true;`
- 别的消息里可以用 `.` 访问，像结构体字段一样

### 保留字段

删掉的字段号要保留，防止后面被复用导致历史数据错乱：

```proto
reserved 2, 15, 9 to 11;
reserved "old_field";
```

### 更新消息

永远不要更改已有字段的编号。加新字段没问题，旧客户端解析新消息时会忽略未知字段，这就是「未知字段」机制，保证向前兼容。

### 其他

- **嵌套类型**：message 里可以嵌套 message，不限层数
- **Any**：可以装任意类型，需要 `import "google/protobuf/any.proto"`
- **oneof**：多个字段共享一块内存，同一时间只设置一个

### Raft协议介绍

是一种共识算法，解决多个节点如何达成一致

核心是Leader， Follower， Candidate， Term（任期）

Raft是工程层比较好实现的方案，因为拆分成了好解决的子问题

演示Raft原理动画

首先是一个单节点系统或数据库，负责存储值，有一个客户端想要把一个值发送给他，系统成功存储，对于一个节点来说非常简单，但对于分布式来说，如何保证多节点数据一致性？

可以归纳为分布式一致性问题，Raft协议设置一个节点有三种状态，第一个是follower，第二个是候选人状态，然后是领导人

一个follower参加竞选，晋升候选人，再竞选，晋升领导者

最开始都是follower，接下来如果跟随者不能从领导者接受消息，则变成候选人，候选人请求其他节点，让他们投票，其他节点如果多数投票，则成为领导者，这个过程叫做领导人选举，之后所有变更有leader决定，客户端发一个数据，先走领导者，领导者首先set数据，形成log，log先不提交，等到把log发送给其他跟随者，收到就回ack，然后跟随者真正执行set数据，，然后领导者再发一个通知是已提交，同步状态。这个过程叫做日志复制

接下来看领导选举的过程

有两个过期时间，第一个叫选举的过期时间，每个节点都有，收不到leader发的消息，过了第一个过期时间，就成功成为候选人，有150-300ms的随机时间，最先超时的人成为候选人后向其他节点请求投票，如果其他节点还没有在他们任期里面投过票，就把票投给候选人，即只能投一票，候选人成为leader后向其他跟随者发送心跳消息，确保自己领导者地位，当leader停了剩下的跟随者继续度过两个超时时间成为新的领导人

每个任期里面只会选中一个领导人

如果有两个节点同时过期，两个节点发起投票，本质就是比谁快谁成为领导人

上面是关于选举状态

下面介绍日志复制

一个节点作为leader接受到客户端的消息set数据消息，给跟随者发送任务日志，跟随者返回ack，收到大多数回复后leader执行set。然后向客户端返回响应，不必等跟随者提交后才发响应，在下一次心跳时发给跟随者让他们执行set数据

raft协议可以保证网络问题时，跟随者收不到信息就会成为新的leader，
